## Context

The `#[schema]` proc-macro (in `selium-guest-macros`) currently bridges Rust structs/enums to Flatbuffers bindings. It generates `FlatMsg`, `HasSchema`, `FieldEncoder` impls plus `write_flatbuffer`/`from_flatbuffer` methods on the annotated type. This works well for monomorphic wire types (e.g., `InterfaceMetadataWire`, `ResourceTargetWire`).

However, generic domain types like `LiveTableMessage<K, V>` cannot be Flatbuffers tables directly — Flatbuffers has no concept of generics. The current pattern requires:

1. A hand-written wire type with `#[schema]` where generics are replaced by `Vec<u8>` (for types serialized via `FlatMsg`) or sentinel values (for `Option<scalar>`)
2. A hand-written `FlatMsg` impl on the domain type that bridges: encode K/V to bytes → wrap in wire → encode wire; decode wire → decode K/V from bytes

This is ~60 lines per generic message type. The macro already knows how to generate all of this — it just needs to be told about the two-type mapping.

### Current state

The `#[schema]` macro parses three parameters: `path`, `ty`, `binding`. It inspects each field's type to determine how to encode/decode it (scalars, `String`, `Vec<u8>`, `Option<T>`, nested `#[schema]` types). The encoding/decoding logic in `schema.rs` is already dispatch-on-type — it would need a new branch for "generic parameter → bytes" but the structure is there.

## Goals / Non-Goals

**Goals:**
- Eliminate the manual wire type and `FlatMsg` bridge impl for generic domain types
- Support automatic detection of which fields need byte-serialization (fields referencing generic params)
- Support `Option<T>` where T is generic (empty bytes = None)
- Support `Option<scalar>` sentinel values (the existing `#[schema]` already handles this — wire types just pass through)
- Generate a wire type struct with a nested `#[schema]` attribute (same `path`/`ty`/`binding` as the domain, applied to the generated wire struct)
- Generate a `FlatMsg` impl on the domain type that delegates through the generated wire type
- Maintain full backward compatibility — existing `#[schema]` usage without `wire` continues to work unchanged

**Non-Goals:**
- Generating `.fbs` schema files — users still write those manually
- Changing the Flatbuffers binding types generated by `flatc`
- Supporting generic structs that map to multiple Flatbuffers tables (unions, etc.)
- Auto-detecting field name mappings from `.fbs` — the naming convention (`key` → `key_bytes`) is hardcoded in the macro
- Changing the `build.rs` pipeline

## Decisions

### Decision 1: `wire` parameter on `#[schema]`

A new optional parameter `wire = WireTypeName` triggers wire type generation. When present, the macro:

1. Generates a new struct `WireTypeName` with the `#[schema]` annotation applied (using the same `path`/`ty`/`binding`)
2. Maps each domain field to a wire field:
   - **Generic param** (`K`) → `{field}_bytes: Vec<u8>`
   - **`Option<generic>`** (`Option<V>`) → `{field}_bytes: Vec<u8>` (empty = None)
   - **`Option<scalar>`** (`Option<u64>`) → `{field}: ScalarType` (sentinel, e.g., 0 = None)
   - **Concrete non-generic** (`u64`, `String`, `Vec<u8>`) → pass through as-is
   - **Nested `#[schema]` type** → pass through as-is
3. Generates `impl<K: FlatMsg, V: FlatMsg> FlatMsg for DomainType<K, V>` that delegates through the wire type

**Rationale**: The `wire` parameter is explicit and opt-in. It doesn't change behavior for existing code. The macro can detect generics automatically from the struct definition — no field-level attributes needed.

**Alternative considered**: Always auto-generate when the struct has generics. Rejected because some generic structs might map to Flatbuffers differently, and explicit is better for a proc-macro with side effects (generating a whole new struct).

### Decision 2: Field name mapping convention

Generic fields get `_bytes` appended to form the wire field name. The `.fbs` schema and Flatbuffers binding must use this same name.

| Domain field | Wire field |
|---|---|
| `key: K` | `key_bytes: Vec<u8>` |
| `value: Option<V>` | `value_bytes: Vec<u8>` |
| `mutation_id: u64` | `mutation_id: u64` |
| `expected_version: Option<u64>` | `expected_version: u64` |

**Rationale**: This matches the existing convention in `live_table.fbs` (`key_bytes`, `value_bytes`). It's predictable and mechanical. The user's `.fbs` must use the same names — mismatches produce compile errors from the Flatbuffers binding, not silent bugs.

**Alternative considered**: Field-level `#[wire(name = "...")]` attributes to override wire field names. Rejected as YAGNI for now — the convention covers the known use case. Can be added later without breaking changes.

**Alternative considered**: Reading the `.fbs` file at macro time to match field names by position or annotation. Rejected as over-complicated and fragile — the macro would need a Flatbuffers schema parser.

### Decision 3: Generic parameter detection

The macro identifies generic parameters from the struct's `syn::Generics`. A field's type "references a generic parameter" if any `syn::TypePath` segment matches one of the declared generic param names. This is a simple string comparison — no type resolution needed.

For `Option<V>` where `V` is generic: the macro strips the `Option` wrapper, sees `V` is a generic param, and treats it as `generic → Vec<u8>` with empty-vec = None.

For `Option<u64>` where `u64` is NOT a generic param: the existing `Option<scalar>` handling already works (sentinel values). This path is unchanged.

**Rationale**: String matching on ident names is the simplest correct approach. The proc-macro has access to the struct's declared generics (`syn::Generics`) and each field's type AST. No need for trait resolution or type analysis.

### Decision 4: Generated code structure

Given:

```rust
#[derive(Debug, Clone, PartialEq)]
#[schema(
    path = "schemas/live_table.fbs",
    ty = "selium.live_table.LiveTableMessage",
    binding = "crate::fbs::selium::live_table::LiveTableMessage",
    wire = LiveTableMessageWire
)]
pub struct LiveTableMessage<K, V> {
    pub mutation_id: u64,
    pub key: K,
    pub value: Option<V>,
    pub expected_version: Option<u64>,
}
```

The macro emits:

1. The cleaned domain struct (without `#[schema]` attribute) — `LiveTableMessage<K, V>`
2. The generated wire struct with `#[schema]` — `LiveTableMessageWire`
3. `impl<K: FlatMsg, V: FlatMsg> FlatMsg for LiveTableMessage<K, V>` — encode/decode through wire
4. `impl<K: FlatMsg, V: FlatMsg> HasSchema for LiveTableMessage<K, V>` — delegates to `LiveTableMessageWireSchema`

The wire struct's `#[schema]` generates items 5-9 (the existing macro output): `LiveTableMessageWireSchema` const, `HasSchema` impl, `FieldEncoder` impl, `new()`, `write_flatbuffer()`, `from_flatbuffer()`, and `FlatMsg` impl — all on `LiveTableMessageWire`.

**Key insight**: The domain type's `FlatMsg` impl does NOT call `FlatMsg::encode` on the wire type (which would double-encode through Flatbuffers). Instead it calls `write_flatbuffer`/`from_flatbuffer` directly:

```rust
// Encode: K,V → bytes → wire struct → write_flatbuffer
fn encode(value: &Self) -> Vec<u8> {
    let key_bytes = FlatMsg::encode(&value.key);
    let value_bytes = match &value.value {
        Some(v) => FlatMsg::encode(v),
        None => Vec::new(),
    };
    let expected_version = value.expected_version.unwrap_or(0);
    let wire = LiveTableMessageWire::new(value.mutation_id, key_bytes, value_bytes, expected_version);
    FlatMsg::encode(&wire)  // <-- this calls write_flatbuffer + finish
}

// Decode: flatbuffers → wire struct → K,V from bytes
fn decode(bytes: &[u8]) -> Result<Self, InvalidFlatbuffer> {
    let wire: LiveTableMessageWire = FlatMsg::decode(bytes)?;
    let key: K = FlatMsg::decode(&wire.key_bytes)?;
    let value: Option<V> = if wire.value_bytes.is_empty() {
        None
    } else {
        Some(FlatMsg::decode(&wire.value_bytes)?)
    };
    let expected_version = if wire.expected_version == 0 { None } else { Some(wire.expected_version) };
    Ok(Self { mutation_id: wire.mutation_id, key, value, expected_version })
}
```

**Rationale**: The existing `FlatMsg::encode` on wire types calls `write_flatbuffer` + `builder.finish()`. The bridge impl needs to call `FlatMsg::encode` on the wire — it can just delegate normally since `FlatMsg` is already generated for the wire type.

### Decision 5: Bounds on generated impl

The generated `FlatMsg` impl requires `K: FlatMsg, V: FlatMsg` (one bound per generic parameter used in byte-serialized fields). The `HasSchema` impl requires the same bounds.

Generic params that appear only in pass-through or sentinel fields don't need the bound — but in practice, a struct where ALL generics are pass-through probably doesn't need the wire generation feature at all.

**Rationale**: Every byte-serialized field calls `FlatMsg::encode`/`FlatMsg::decode` on its value, so the bound is required. Emitting bounds only for actually-used params is more precise but adds complexity for negligible benefit.

## Risks / Trade-offs

- **Naming mismatch**: If the user's `.fbs` uses `key_data: [ubyte]` but the macro generates `key_bytes: Vec<u8>`, the Flatbuffers binding won't compile against the wire struct. → Mitigation: The compile error will be clear (missing field in generated Args struct). The `_bytes` convention is documented and matches the existing pattern.

- **Macro complexity**: The `expand_struct` function grows from ~120 lines to ~250 lines. → Mitigation: Extract helper functions for wire struct generation and bridge impl generation. The logic is additive, not entangled.

- **`#[schema]` on wire type without `wire` parameter**: If someone accidentally puts `#[schema]` on a generic struct without `wire`, the existing macro will try to generate Flatbuffers encode/decode for generic fields and fail (because `K` doesn't implement the Flatbuffers field accessor pattern). → Mitigation: The macro can detect generic params and emit a helpful compile error: "use `wire = WireTypeName` to generate wire type for generic structs".

- **Multiple generic messages**: As more generic message types are added, each follows the same pattern. → The design generalizes — it's not specific to `LiveTableMessage`.

## Migration Plan

1. Implement the `wire` parameter and generation logic in `selium-guest-macros`
2. Update `LiveTableMessage` in `tables.rs`:
   - Add `#[schema(wire = LiveTableMessageWire, ...)]` to `LiveTableMessage<K, V>`
   - Remove the manual `LiveTableMessageWire` struct
   - Remove the manual `FlatMsg` and `HasSchema` impls for `LiveTableMessage<K, V>`
3. Run existing tests to verify round-trip behavior is preserved
4. No changes to `.fbs` files, `build.rs`, or Flatbuffers bindings

Rollback: The manual pattern still works. If the generator has issues, revert to the explicit two-type approach.

## Open Questions

1. **Should `Option<generic>` where the inner generic is a scalar (e.g., `Option<u64>` where `u64` is actually a type alias for a generic) be handled?** Currently scalar detection is by ident name (`"u64"`, `"u32"`, etc.), not by generic parameter lookup. If someone writes `struct Foo<T = u64> { x: Option<T> }`, the macro will see `T` as generic and generate `x_bytes: Vec<u8>`, not `x: u64`. Is this correct? Probably — if it's generic, it should be treated as opaque bytes.

2. **Should we support `#[schema(wire = ...)]` without generics?** A non-generic struct with `wire` would generate an identical wire type (no field transformations). This could be useful for separating domain and wire concerns but isn't needed now. Start with generics-only and relax later if needed.
