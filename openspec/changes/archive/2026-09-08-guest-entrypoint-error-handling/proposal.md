## Why

Guest entrypoint error handling grew two inconsistent conventions. A
`Context`-leading entrypoint used to receive a raw `u64` discovery handle
and construct its own context with `Context::from_raw(discovery_handle)`
in the function body — but the `#[entrypoint]` macro already generates a
`Context` from the first argument slot, so guests were duplicating macro
behaviour. Worse, that generated construction used `.expect(...)`, so even
a `Result`-returning entrypoint — which otherwise fails gracefully,
logging the error and exiting 1 — hard-panicked on a bad bootstrap handle.
Custom error types were also hand-rolled (`impl std::error::Error` +
manual `Display`), while the rest of the workspace (guest SDK, wire,
runtime, abi) standardised on `thiserror::Error` derives.

## What Changes

- **`selium-guest-macros`**: `Context::from_raw` in the generated
  entrypoint glue propagates via `?` when the entrypoint returns
  `Result<(), E>` — a failed bootstrap handle becomes a logged, graceful
  exit (code 1). Infallible `()` entrypoints keep the explicit
  `.expect` hard-abort (they have no error channel).
- **`selium-guest`**: `Context` stores the raw discovery handle and
  exposes `Context::raw_handle()`, so system guests that must forward
  the handle to spawned child guests (bridge → bridge-channels) no
  longer reconstruct it manually. `run_entrypoint_with_result` no longer
  panics when a `Result` entrypoint parks before completing (the normal
  state for long-running service guests such as discovery): the export
  reports exit code 0, the task stays on the reactor, and its eventual
  error is logged when it completes.
- **Guests**: every fallible `#[entrypoint]` now returns
  `anyhow::Result<()>`, converting startup errors through `?` /
  `with_context` / `bail!` instead of `match`-then-`return;` blocks.
  Failure messages keep their meaning through the anyhow context chain
  and surface as the process's final `error!` log.
- **Error types**: all remaining `impl std::error::Error for X {}`
  manual impls (connector `TlsError` ×2, connector `ForwardError`,
  wire `RpcError`, guest `HttpServeError`, guest log `InitError`,
  proto-dns `WireError`, plus one test error) become
  `#[derive(thiserror::Error)]` with per-variant `#[error("...")]`
  messages. `thiserror` joins the connector guests and proto-dns
  crates (already present in guest, wire, runtime, abi).
- **BREAKING**: none. `Display` strings, exit codes, and the ABI are
  unchanged; `impl Error` and `Display` are generated by the derive
  instead of written by hand. Wrapped-error variants now also expose a
  `source()` (`RpcError::Remote`/`Serialization`-style fields are plain
  strings and carry none).
- **Docs**: `selium-runtime`'s discovery-handle wording is corrected
  (guests no longer manually call `Context::from_raw`), and the stale
  example in `SystemGuestDescriptor::set_discovery_handle` is updated.

## Capabilities

### New Capabilities

(None — this extends existing capabilities; see Modified.)

### Modified Capabilities

- `selium-guest-macros`: `Context-Aware Entrypoint Parameter` gains
  bootstrap-handle failure semantics per return kind; `Result
  Entrypoint Error Type Validation` documents thiserror-derived error
  types as accepted.
- `selium-runtime`: discovery-handle delivery wording updated — the
  handle is prepended as the first argument slot and the entrypoint
  macro constructs the `Context`; guests no longer call
  `Context::from_raw` themselves.
- `selium-guest`: new requirement for the `Context::raw_handle()`
  accessor (public SDK behaviour for handle-forwarding guests); the
  `Entrypoint Result Extraction` requirement is modified for parked
  entrypoints (a long-running service reports exit code 0 and keeps
  running; errors are logged whenever the task completes).

## Impact

- `crates/guest`: `context.rs` (handle field + `raw_handle()`),
  `log.rs` (`InitError`), `net/http.rs` (`HttpServeError`).
- `crates/guest/macros`: generated `Context` prelude branches on return
  kind (`?` vs `.expect`); `tests/result_entrypoint.rs` uses thiserror;
  `thiserror` dev-dependency added.
- `crates/wire` (`rpc.rs` `RpcError`), `crates/proto-dns` (`wire.rs`
  `WireError` + `thiserror` dep), `crates/runtime` (`config.rs` docs).
- Guests: `anyhow` (`features = ["std"]`) already added to 10 guests;
  connector-quic / connector-http add `thiserror`; `TlsError` ×2 and
  `ForwardError` converted. Four infallible entrypoints (external-api,
  supervisor, scheduler, cluster) intentionally unchanged.
- Tests: guest SDK, guest-macros, wire, proto-dns, runtime suites; all
  guest `wasm32-unknown-unknown` builds (anyhow/thiserror are
  compile-time, std is available on the target).
